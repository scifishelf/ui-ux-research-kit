# Web excellence audit

Audit authorization covers analysis and planning; respect separately granted implementation/installation permission without extending it.

The complete kit is two levels above this skill directory. Read [the universal workflow](../../reference/universal-audit.md). For a separately installed skill, locate the complete kit from the assignment and pass `--kit`; criteria and registries are not duplicated inside the skill.

1. **Understand the product.** Read target/project rules. Identify frontend, stack, startup path, audience and priority user jobs. Decide website/webapp/pwa and feature applicability. For an explicit development-setup audit, additionally use [pipeline-audit](../pipeline-audit/SKILL.md).
2. **Create a baseline.** Review the startup commands and start the app first, so files it writes cannot invalidate the baseline; installing its dependencies needs installation permission, and without a running app runtime criteria stay unknown. Run `scripts/audit.py --target <repo-root> --out <run-directory> --kit <kit-root>` for inventory hints (`discovery` in `audit.json`; in a monorepo the run lists the candidates and exits, rerun with `--frontend <path>`), save the step 1 decisions as `<run-directory>/project.json` (from [project.example.json](../../reference/project.example.json)) and rerun with `--project`. Respect the requested artifact destination; if output must stay inside the target, keep everything including kit copies inside `--out`.
3. **See and use the product.** Work through the investigations in the baseline `action-plan.md`: each gives the criterion's test (steps) and pass condition (quality target). Use the existing local runtime/browser tools under their operating rules; save every artifact under `<run-directory>/evidence` and write nothing into the target. Render relevant journeys, states and viewports; actually inspect screenshots and perform interactions. Check DOM/accessibility, console/network and suitable traces, plus manual keyboard/screen-reader behavior. For a blocked check record `status: unknown` with the blocker in `reason` and continue independent work. Use an actual suitable runtime for installed PWA and software-keyboard checks.
4. **Record concrete findings.** Copy `observations.template.json` to `observations.json` and fill it using the [evidence contract](../../reference/universal-audit.md#evidence-contract) and [schema](references/observations.schema.json). A pass covers the criterion's coverage matrix; partial tests stay unknown. Each fail needs the `remediation` defined there. Merge several defects of one criterion into one finding. Verify the source cause before naming `affected_files`; invent no files or defects. The checker verifies files, hashes and bindings, not that you looked. After source/scope changes rerun the baseline and retest before reusing observations.
5. **Deliver the plan.** Apply [product critique](../../rubrics/product-critic.md) to actual screens and flows. Rerun with `--observations` and `--evidence-root`; check `action-plan.md` for dependencies and product-specific completeness and correct gaps in `observations.json`, never in generated files (every run overwrites them). A critique gap that maps to a criterion becomes a `fail` observation before the rerun; everything else goes into `REPORT.md` ([contents](../../reference/universal-audit.md#action-plan-and-acceptance)). State estimates and uncertainty.
6. **Recommend suitable capabilities.** Follow [skill and tool proposals](../../reference/universal-audit.md#skill-and-tool-proposals): reuse existing capabilities, bind additional skills to observed gaps and the actual stack, and state source, installation option, whether pin and license were reviewed, pilot and retest.

Record the requested report language in `project.json` as `report_language` (English default). The checker emits English templates and records the preference; it does not translate. Translate generated Markdown in place only after the final run, preserving evidence, uncertainty, JSON keys, IDs, statuses, paths and commands.

Deliver the files listed under [action plan and acceptance](../../reference/universal-audit.md#action-plan-and-acceptance) with build/scope provenance. If no target is supplied, prepare the invocation rather than inventing a product. An audit can end with open criteria if `REPORT.md` names the blocker and what was attempted for each; acceptance additionally requires that evidence and human design/user review.
